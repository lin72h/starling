The SDK · why & what

Flutter's framework, in Swift, with no VM

Widgets, rendering, painting, gestures and semantics — ported to Swift and driven directly by the Flutter engine's C core. The Dart isolate is gone; everything else about Flutter stays. This is the piece the Starling desktop is written in, and it runs on an ordinary Linux desktop too.

The question

“Why not just use Dart?”

It is the first thing anyone from the Flutter community asks, and it is a fair question. Dart is a good language. Flutter's framework is written in it, beautifully. Rewriting a hundred thousand lines of it in another language is not something you do because you dislike the syntax.

We did it because of what we were building. Starling is not an app that runs on a desktop — it is the desktop: a Wayland compositor, a window manager, an X11 server, a portal service, and the apps on top. That workload spends its life doing two things Dart is deliberately designed not to do. It shares memory across threads, and it calls C.

What follows is the systematic version of that answer. None of it is a criticism of Dart for the job Dart was designed for — writing apps. It is an argument about a different job.

The case

Four reasons, in order of how much they mattered

01Real threads that share memory

Dart's concurrency model is isolates: separate heaps, no shared mutable state, communication by copying messages. That model is a genuine feature — it makes data races structurally impossible, and for app code it is usually the right trade. But a compositor does not get to choose. A frame arrives on the engine's raster thread, a client buffer arrives on a socket thread, input arrives from libinput, and all of them touch state that the UI thread is also reading, at 30 to 60 times a second.

In Swift that is ordinary code: a lock, an atomic, a class shared between threads, with Sendable and actors when you want the compiler checking you. Starling's screen recorder ingests frames on the engine's writer thread and hands them to a hardware encoder without copying a pixel — the buffers are shared memory, because in a compositor a 4K frame crossing an isolate boundary as a copy is not a design, it is a budget you have already spent.

To be precise about what did not change: the framework's element tree is still single-threaded, exactly as in Flutter. You build UI on one thread. The difference is that everything around the UI can be genuinely concurrent and still share memory with it.

02C and C++ at zero cost, with no bindings layer

Swift imports a C header as a module. You write import WaylandServerBridge and then call wayland_server_keyboard_key(…) like any other function — no binding declarations, no code generator, no marshalling step, no separate .dart file describing a struct you already described in a header. Structs come across as structs. Function pointers come across as closures. C++ interop is a build setting.

Dart can call C through dart:ffi, and it works, but it is a bridge: bindings are declared or generated, memory is managed by hand through Pointer, and callbacks back into Dart carry rules about which isolate they may run on. For an app calling one library that is a small tax. For the Starling shell — which talks to DRM/KMS, GBM, EGL, libinput, xkbcommon, dma-buf, sd-bus and PipeWire, and passes file descriptors between processes — the tax would be most of the program.

03No VM in the process

Swift compiles ahead of time to native code with reference counting, so there is no interpreter, no JIT warm-up and no tracing garbage collector deciding when to pause. For a compositor that is worth real money: a collection pause does not drop a frame in your app, it drops a frame for every app on the screen at once.

The honest version is that ARC is not free either — retain and release traffic has a cost, and it is deterministic rather than absent. But the cost is spread evenly and it is yours to see in a profile, which is a different kind of problem from a pause you did not schedule. Removing the VM also removes an entire runtime from the process: the engine's C core is still there, and above it there is now just your code.

04The code you already know how to write

This one is the reason the port was feasible at all. Swift and Dart are close relatives — classes, generics, closures, named arguments, optionals, trailing-closure syntax. The framework port is a near-mechanical translation, not a reimagining, which means Flutter's own documentation, its widget catalogue and fifteen years of accumulated answers all still apply.

The clearest way to show that is the app everyone has already typed. Here is flutter create's counter, in Dart, and the same program in the Starling SDK.

Side by side

The counter app, both ways

Dart — Flutter
class _MyHomePageState extends State<MyHomePage> {
  int _counter = 0;

  void _incrementCounter() {
    setState(() {
      _counter++;
    });
  }

  @override
  Widget build(BuildContext context) {
    return Scaffold(
      appBar: AppBar(title: Text(widget.title)),
      body: Center(
        child: Column(
          mainAxisAlignment: MainAxisAlignment.center,
          children: [
            Text('You have pushed the button…'),
            Text('$_counter'),
          ],
        ),
      ),
      floatingActionButton: FloatingActionButton(
        onPressed: _incrementCounter,
        child: Icon(Icons.add),
      ),
    );
  }
}
Swift — Starling SDK
class _MyHomePageState: State<StatefulWidget> {
  private var _counter = 0

  private func _incrementCounter() {
    setState {
      _counter += 1
    }
  }

  override func build(_ context: any BuildContext) -> Widget {
    let homePage = widget as! MyHomePage
    return MaterialScaffold(
      appBar: MaterialAppBar(title: homePage.title),
      body: Center(
        child: Column(
          mainAxisAlignment: .center,
          children: [
            Text("You have pushed the button…"),
            Text("\(_counter)"),
          ]
        )
      ),
      floatingActionButton: MaterialFloatingActionButton(
        onPressed: { [weak self] in self?._incrementCounter() },
        child: Icon(CupertinoIcons.add)
      )
    )
  }
}

Same structure, same lifecycle, same setState. The differences are Swift's, not ours: override func instead of @override, a capture list on the closure, and enum cases that shorten to .center because the type is already known. Someone who writes Flutter can read this on the first try, which is the entire point.

There is one addition. Because Swift has result builders, every container also takes a trailing closure, so if, for and switch work directly inside a widget tree — no ...[ spread operators, no .map().toList(). Both spellings compile to the identical tree; a lint in the repo keeps them from drifting apart.

Scope

It is not only for our desktop

The SDK was extracted from Starling, which is its largest consumer but was never meant to be its only one. It ships the framework and the thin platform bindings needed to host an engine, and nothing desktop-specific.

Concretely: swift run FlutterDemo opens a window on whatever Linux session you already use — GNOME on Wayland, KDE, X11. That host is the engine's own GTK embedder, an FlView inside a GtkWindow, started in Swift mode. Window management, input, IME and accessibility all come from the same code path a normal Flutter Linux app uses. The Swift framework replaces the Dart isolate and nothing else.

A Starling SDK app is an ordinary native Linux application. It does not need the Starling desktop, or know that one exists.

There are two ways to depend on it, depending on how you want the engine to arrive. As a versioned SwiftPM package, the engine comes in as a static binary artifact and your executable ends up self-contained — nothing to ship beside it. As a downloaded bundle, the engine is a shared library and a fleet of apps loads one copy, which is the shape the Flutter SDK itself has, and what Starling uses.

Honest status

What runs today, and what is planned

We would rather be believed than impressive, so this table is the real state rather than the roadmap.

Linux tested
The tested platform. Runs under the Starling desktop on DRM/KMS, and on an ordinary desktop session through the GTK host. The bundle tooling builds per-architecture trees; the versioned static-artifact route publishes x86_64 today, and more triples can be added to it.
macOS planned
The package manifest has a macOS branch and a FlutterMacOSBridge target against the macOS embedder, but nothing verifies them yet — that needs a machine and CI, and until it has both we will not claim it works. It is the next platform we intend to finish.

Known gaps

The framework does not yet answer System.requestAppExit, so a host closes its window directly rather than letting the framework veto. The flutter/keyevent channel replies are not yet the JSON the GTK keyboard handler expects, which logs a warning on focus changes. And on Ubuntu 26.04 a toolchain-versus-distro mismatch means consumers need two extra compiler flags — the workaround is in the repo and disappears when swift.org ships a native 26.04 toolchain.

Try it

The framework, the bridges, the GTK host and the ported samples — the counter above, a todo app, a calendar package port — are all in one repository, and the demo runs on the desktop session you are already using.
