Starling Desktop · Performance Report

What screen recording costs the app on screen

One application, one binary — the ghostty terminal — runs on three Wayland desktops on the same machine, all recording with the same hardware H.264 encoder. First, just rendering: the same binary moves ~27% more data per second on Starling (40 vs ~32 MB/s) — a pacing tradeoff §2 lays out in full, not a raw-speed claim. Then, recording the screen while it runs: GNOME slows it ~6% and Hyprland ~11%; Starling slows it ~4% while delivering the full 30 fps — including every frame GNOME drops. 1 · The measurement

The workload is a terminal rendering a continuous hex dump of /dev/urandom — full-screen text with no frame-to-frame redundancy, the worst case for a video encoder. The producer is unthrottled: it writes exactly as fast as the terminal accepts, so the terminal’s throughput (bytes/s accepted, read from the producer’s wchar counter in /proc) is a live probe of how fast the whole display path is running. If recording slows the desktop’s frame delivery, throughput falls — even when no process looks CPU-bound.

Each run is three 120 s windows: baseline, recording, baseline again. The cost of recording is the throughput drop in the middle window against the mean of the flanking baselines; every run reports its baseline drift (≤0.01 cores in almost all final runs). All recordings target 30 fps at 2560×1600 with hardware H.264 (VAAPI) on every desktop. Earlier exploratory runs used 20–25 s windows; those systematically overstated GNOME’s cost (−12% apparent vs −6.3% at two minutes), because pipeline warm-up and session-settling drift occupy a large fraction of a short window. They are superseded and omitted here; every run remains in this report’s git history.

2 · First: just render — the same binary, three compositors

Before measuring what recording costs, measure the floor it stands on: with no recording at all, how fast does the same application run on each desktop? A Wayland client’s throughput on this workload is set by how quickly the compositor turns commits around — frame callbacks are the clock the client draws by. 4 · The mechanism, traced to source

Why does the recorded app slow down when the encoder is nearly free and CPUs are idle? Because on GNOME, every captured frame re-renders the entire screen a second time, inside the compositor, on the same GPU and main thread the app depends on.

In mutter 50.1 (the exact version measured), the screencast “area” stream’s frame producer calls clutter_stage_paint_to_framebuffer() unconditionally — a full walk and repaint of the scene graph into the capture buffer. meta-screen-cast-area-stream-src.c:record_to_framebuffer  There is no copy path in that file at all. And GNOME’s own recording service always requests an area stream, even for whole-screen capture. gnome-shell screencastService.js: RecordAreaSync

The irony: mutter’s monitor stream source already contains the cheap alternative — a one-step GPU blit of the existing framebuffer, and a direct copy of the client’s buffer on direct-scanout frames. meta-screen-cast-monitor-stream-src.c:770, :745  GNOME’s recorder never reaches it. A merge request making the area path reuse the monitor framebuffer — its description says the stage “would be painted a second time” otherwise — has been open, unmerged, since February 2021 (mutter !1711).

The chain from there to a slower application has three links, each verified. The extra composition occupies the compositor’s main thread — the same thread that dispatches input, Wayland requests, and frame scheduling — and the same integrated GPU the app renders with. A busy compositor delivers frame callbacks late, and a Wayland client only draws when its frame callback arrives. A terminal that only reads from the pty while preparing to draw therefore reads less — which is the throughput drop in Fig 1, and why the terminal used less CPU while recording: it was waiting for its turn, not starved of cycles.

This is not GNOME-specific carelessness: Hyprland’s wlroots screencopy path pays a comparable tax (−11.4%) through a different mechanism. Copy-based capture inserted into the present path is simply what current compositors do.

Three runtime confirmations

  • The repaint is observable. With MUTTER_DEBUG=screen-cast, a 12 s recording logged 329 “Recording full frame” events — each one a full 2560×1600 composition — and 754 throttle skips, each of which queues synthetic damage that keeps the compositor’s frame clock hot.
  • The cost scales with capture rate. Setting the recording frame rate to 1, 5, and 30 fps produced −3.9%, −10.7%, −17.4% workload slowdown (Fig 4): a per-captured-frame cost, not a fixed session cost.
  • It is not CPU or encoder contention. The slowdown persists with the encoder at 0.02 cores and 13 of 16 cores idle; the terminal uses less CPU while producing less — the signature of waiting for frame callbacks, not of starvation.

5 · Why Starling pays a fraction of it

Starling’s recorder never re-renders. At each present, the engine blits the frame it already composited into a dma-buf ring — a flat GPU copy, not a scene walk — and hands the buffer straight to the AMD VCN encoder. The blit is paced against an absolute 33.3 ms schedule at the source, so presents between capture slots cost nothing and a slot missed to client jitter is repaid by the next present — which is why delivery holds a flat 30.00 fps. The CPU never touches a pixel: during recording the only new CPU consumer on the whole system is a kernel VCN worker (kworker/…vcn_enc) and ~0.02–0.07 cores of bookkeeping.

The ~4% that remains is the capped 30/s blit itself, riding the presenting thread ahead of the swap. What Starling never pays is the term that dominates on GNOME — there is no second composition of the scene, ever.

7 · What this report does not claim

  • Not a visual-quality comparison. Each run recorded different random content, so per-frame quality metrics between desktops are not computable; the bitrate column is not an efficiency ranking.
  • Grids are matched, not identical. The same terminal (ghostty 1.3.0) ran on all three desktops for the headline comparison, at 8,500 cells on GNOME/Hyprland and 7,644 cells (90%) on Starling — the closest its cell-quantized sizing allows at the panel’s scale. The metric is each configuration’s change against its own baseline, so the grid difference divides out of the slowdown comparison (it does not divide out of the §2 baseline comparison, where it is accounted for in the text).
  • Two conventional probes favor the other compositors. GNOME and Hyprland deliver frame callbacks at the panel’s full 90 Hz where Starling paces near 50 fps, and both score ~4× higher on unthrottled glmark2 — see the table in §2. Latency-sensitive and animation-heavy workloads may prefer that behavior; input-to-photon latency was not measured. Starling’s advantages in this report are app throughput and recording behavior, not frame-loop rate.
  • The baseline comparison (§2) carries a confound the slowdown numbers do not. Baselines were measured in different login sessions hours apart, and ghostty’s session-to-session spread on GNOME reached several MB/s in exploratory runs. Across every session measured on this box, Starling’s ghostty baselines stayed in a 39.4–44 MB/s band; GNOME’s best exploratory session reached ~39.6 with the rest at 31–38, and Hyprland’s peaked at 36.5 — the distributions overlap only at their extremes, and the matched final runs (Fig 4) show the gap under the cleanest conditions. A same-session A/B (one login each, back to back) would remove this confound entirely and is cheap to run.
  • Window length changes the answer. 20–25 s windows measured GNOME at −12% and Hyprland at −13.9%; two-minute windows give −6.3% and −11.4%. Short windows overstate cost (warm-up and drift dominate) — which is why the final protocol is two minutes, and why both sets are published. The mechanism evidence (Fig 4, the debug-log repaints) is unaffected.
  • One machine. AMD iGPU, 90 Hz HiDPI panel. Ratios will differ elsewhere; the mechanism (per-frame recomposition on the shared GPU/main thread) will not.
  • GNOME’s numbers are its best case. A stock Ubuntu install lacks gstreamer1.0-plugins-bad, so GNOME’s recorder silently falls back to software VP8 — measured far worse in exploratory runs (an encoder near 7 CPU cores and a −54% workload hit at short windows). Hardware encode was installed and verified before any headline number here was taken.

8 · Reproduce it

Load, on the desktop under test (unthrottled by design — measure throughput, not CPU%):

# fullscreen terminal
xxd /dev/urandom

Measure: sample every process’s CPU from /proc/*/stat and the producer’s wchar from /proc/<xxd>/io over baseline → recording → baseline windows; start GNOME’s recorder over D-Bus (org.gnome.Shell.Screencast) on a connection you keep open. Confirm the mechanism live with MUTTER_DEBUG=screen-cast and count “Recording full frame” lines. Full harness scripts: screencast-bench.py, starling-rec-bench.py, hypr-rec-bench.py, ab-capture.py, cbjitter.c (the frame-callback probe) — checked into the Starling repo under docs/perf/recording-cost-2026-08-04/ beside this report (~150 lines each, no dependencies beyond PyGObject).

Measured 2026-08-04 on one machine by an automated harness; all runs, including unfavorable ones, are reported. Mutter source citations refer to tag 50.1 (matching the installed libmutter-18-0 50.1-0ubuntu2.2).
