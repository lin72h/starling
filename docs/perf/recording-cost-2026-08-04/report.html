Starling Desktop · Performance Report

What screen recording costs the app on screen

One application — the ghostty terminal — runs on three Wayland desktops on the same machine. While a screen recording runs, GNOME slows it ~6% and Hyprland ~11%; Starling slows it ~4% and still delivers the frames GNOME drops. Before any recording starts, the same app simply runs faster on Starling’s compositor (41 vs ~32 MB/s) — and Starling’s native terminal, riding the platform’s own app path instead of the Wayland protocol, is faster still. Numbers, mechanism, and the defect this method found in our own path, below.

1 · The measurement

The workload is a terminal rendering a continuous hex dump of /dev/urandom — full-screen text with no frame-to-frame redundancy, the worst case for a video encoder. The producer is unthrottled: it writes exactly as fast as the terminal accepts, so the terminal’s throughput (bytes/s accepted, read from the producer’s wchar counter in /proc) is a live probe of how fast the whole display path is running. If recording slows the desktop’s frame delivery, throughput falls — even when no process looks CPU-bound.

Each run is three 120 s windows: baseline, recording, baseline again. The cost of recording is the throughput drop in the middle window against the mean of the flanking baselines; every run reports its baseline drift (≤0.01 cores in almost all final runs). All recordings target 30 fps at 2560×1600 with hardware H.264 (VAAPI) on every desktop — GNOME’s out-of-the-box software-VP8 configuration is shown separately, because it is what users actually get by default. Earlier exploratory runs used 20–25 s windows; those systematically overstated GNOME’s cost (−12% apparent vs −6.3% at two minutes), because pipeline warm-up and session-settling drift occupy a large fraction of a short window. They are retained in the data table, labeled, and superseded.

A Wayland client’s throughput on this workload is set by how quickly the compositor turns commits around — frame callbacks are the clock the client draws by. 3 · The mechanism, traced to source

Why does the recorded app slow down when the encoder is nearly free and CPUs are idle? Because on GNOME, every captured frame re-renders the entire screen a second time, inside the compositor, on the same GPU and main thread the app depends on.

In mutter 50.1 (the exact version measured), the screencast “area” stream’s frame producer calls clutter_stage_paint_to_framebuffer() unconditionally — a full walk and repaint of the scene graph into the capture buffer. meta-screen-cast-area-stream-src.c:record_to_framebuffer  There is no copy path in that file at all. And GNOME’s own recording service always requests an area stream, even for whole-screen capture. gnome-shell screencastService.js: RecordAreaSync

The irony: mutter’s monitor stream source already contains the cheap alternative — a one-step GPU blit of the existing framebuffer, and a direct copy of the client’s buffer on direct-scanout frames. meta-screen-cast-monitor-stream-src.c:770, :745  GNOME’s recorder never reaches it. A merge request making the area path reuse the monitor framebuffer — its description says the stage “would be painted a second time” otherwise — has been open, unmerged, since February 2021 (mutter !1711).

The chain from there to a slower application has three links, each verified. The extra composition occupies the compositor’s main thread — the same thread that dispatches input, Wayland requests, and frame scheduling — and the same integrated GPU the app renders with. A busy compositor delivers frame callbacks late, and a Wayland client only draws when its frame callback arrives. A terminal that only reads from the pty while preparing to draw therefore reads less — which is the throughput drop in Fig 1, and why the terminal used less CPU while recording: it was waiting for its turn, not starved of cycles.

This is not GNOME-specific carelessness: Hyprland’s wlroots screencopy path pays a comparable tax (−13.9%) through a different mechanism. Copy-based capture inserted into the present path is simply what current compositors do.

Three runtime confirmations

  • The repaint is observable. With MUTTER_DEBUG=screen-cast, a 12 s recording logged 329 “Recording full frame” events — each one a full 2560×1600 composition — and 754 throttle skips, each of which queues synthetic damage that keeps the compositor’s frame clock hot.
  • The cost scales with capture rate. Setting the recording frame rate to 1, 5, and 30 fps produced −3.9%, −10.7%, −17.4% workload slowdown (Fig(Fig 4): anbsp;5): a per-captured-frame cost, not a fixed session cost.
  • It is not CPU or encoder contention. The slowdown persists with the encoder at 0.02 cores and 13 of 16 cores idle; the terminal uses less CPU while producing less — the signature of waiting for frame callbacks, not of starvation.

4 · Why Starling pays a fraction of it

Starling’s recorder never re-renders. At each present, the engine blits the frame it already composited into a dma-buf ring — a flat GPU copy, not a scene walk — and hands the buffer to the AMD VCN encoder. The CPU never touches a pixel; during recording, the only new CPU consumer visible on the whole system is a kernel VCN worker (kworker/…vcn_enc) and ~0.02–0.07 cores of bookkeeping.

The copy is cheap, not free: it rides the engine’s presenting thread ahead of the swap, and against a fast client it showed up as a residual ~5%. Applying this report’s own method to that residual found a defect: the capture ran once per present with no rate cap of its own — the shell held the encoded rate to 30 fps by discarding frames downstream, after each had already paid for its full-resolution copy. Capping capture at the source (engine f9c06aee0b3, shell 0908f9d: presents inside the interval skip capture before touching the GPU) improved the short-window measurement from −4.7% to −3.4%; at the final two-minute protocol the cost is −4.1% with ghostty and −2.6% with the native terminal. The remainder is the capped 30/s blit itself in the present path. Notably, the native terminal was heavily optimized between the exploratory and final runs (13.9 → 48 MB/s on this workload) — as a slow client it had measured within noise; as a fast one it pays the same per-present tax the model predicts. Both configurations avoid the term that dominates on GNOME — there is no second composition of the scene, ever.

Taken together with §2, the native path wins on both sides of the ledger: it posts the highest raw throughput on the box (48 MB/s, Fig 4) and the lowest recording tax (−2.6%, Fig 1) — a first-party app compositing through the platform’s own texture path rather than the Wayland protocol gives up nothing to get recorded.

6 · What this report does not claim

  • Not a visual-quality comparison. Each run recorded different random content, so per-frame quality metrics between desktops are not computable; the bitrate column is not an efficiency ranking.
  • Grids are matched, not identical. The same terminal (ghostty 1.3.0) ran on all three desktops for the headline comparison, at 8,500 cells on GNOME/Hyprland and 7,644 cells (90%) on Starling — the closest its cell-quantized sizing allows at the panel’s scale. The native-terminal configuration (5,694 cells, ~90% screen coverage) is reported separately. The metric is each configuration’s change against its own baseline, so terminal and grid differences divide out of the comparison.
  • The baseline comparison (§2) carries two confounds the slowdown numbers do not. Cross-session variance: baselines were measured in different login sessions hours apart, and ghostty’s session-to-session spread on GNOME reached several MB/s in exploratory runs — though Starling’s worst session baseline (39.2) still exceeded GNOME’s and Hyprland’s best. And the native-terminal lane is a different program at a smaller grid: it demonstrates the native app path out-running the best Wayland terminal on this box, not a controlled protocol-vs-protocol measurement. The controlled version — one renderer, two transports — is future work.
  • Window length changes the answer. 20–25 s windows measured GNOME at −12% and Hyprland at −13.9%; two-minute windows give −6.3% and −11.4%. Short windows overstate cost (warm-up and drift dominate) — which is why the final protocol is two minutes, and why both sets are published. The mechanism evidence (Fig 4, the debug-log repaints) is unaffected.
  • One machine. AMD iGPU, 90 Hz HiDPI panel. Ratios will differ elsewhere; the mechanism (per-frame recomposition on the shared GPU/main thread) will not.
  • GNOME’s numbers are its best case — hardware encode was installed and verified for this test. The shipping default is the −54%/7.55-core row.

7 · Reproduce it

Load, on the desktop under test (unthrottled by design — measure throughput, not CPU%):

# fullscreen terminal
xxd /dev/urandom

Measure: sample every process’s CPU from /proc/*/stat and the producer’s wchar from /proc/<xxd>/io over baseline → recording → baseline windows; start GNOME’s recorder over D-Bus (org.gnome.Shell.Screencast) on a connection you keep open. Confirm the mechanism live with MUTTER_DEBUG=screen-cast and count “Recording full frame” lines. Full harness scripts: screencast-bench.py, starling-rec-bench.py, hypr-rec-bench.py, ab-capture.py — checked into the Starling repo under docs/perf/recording-cost-2026-08-04/ beside this report (~150 lines each, no dependencies beyond PyGObject).
